# Architecture review: the assistant against current best practice

Written 28 October 2026. This review compares the code on `main` with published guidance on building AI assistants and agents (2024–2026). It covers the design, not the UI. Read it alongside `docs/USABILITY_FIXES.md`. Item numbers such as "UF-15" refer to that file.

Sources are numbered [S1], [S2] and so on. The full list is in section 5.

---

## 1. Summary

**What already matches best practice**

- **Writes are safe by design.** The model can only *propose* a write. The proposal is stored with a hash. Approval re-checks permission, state and payload, and runs once (`services/tools/registry.py:propose_write`, `api/chat.py:approve_action`). This is the human-in-the-loop pattern that OpenAI and OWASP recommend for high-risk actions [S3][S9]. It is stronger than most ERP copilots describe publicly.
- **Permissions come from Frappe, not the prompt.** Every read goes through `get_list`, `has_permission` or `DatabaseQuery` with `ignore_permissions=False`. Field-level read permission is checked on filters, and RAG chunks are filtered by role. Salesforce, Microsoft and SAP describe the same rule: the assistant sees what the user sees [S11][S12][S13].
- **There is no free-form SQL.** The model only fills DocType, filter and field arguments. That avoids most text-to-SQL risk [S10].
- **Workflow first, agent second.** Gates, deterministic shortcuts, then a bounded tool loop (4 rounds, deadline, daily cap), then a fallback. This is the "workflows for well-defined tasks, agents only where needed" shape in Anthropic's guide [S1]. A rewrite is not justified.

**The biggest gaps**

- **The DocType is chosen by about 1,400 lines of hand-written phrase and regex rules** (`services/targeting.py`, `services/intent.py`), and those rules can **override the model's own choice** (`targeting.py:canonical_doctype` runs on every tool call). Each new wording needs a new rule, and a wrong rule wins silently. This is the root cause behind UF-15 and part of UF-16.
- **Numbers are not grounded end to end.** The model writes the sentence that holds the number. The "Checked: …" line added in UF-15 shows the mismatch but does not prevent it. Best practice is to build the number from the tool result and let the model write only the words around it [S1][S6].
- **There is no evaluation set run against the real model.** Tests mock the model, so the wrong-count and lost-context bugs reached live testing. Anthropic's guidance is to start with 20–50 tasks taken from real failures and re-run them on every change [S5].
- **Conversation state is rebuilt from text.** Session facts come from regexes on the message (`conversation.py:extract_session_facts`) and are stored inside a 1,200-character summary string. Follow-ups work today (UF-16), but they depend on more word lists (`run_chat.py:_BACK_WORDS`).
- **Tool schemas are loose, there is no trace you can replay, and latency has not been tuned** (no strict schemas, no prompt-cache-friendly ordering, a live web fetch for how-to answers, and an older default model).

## 2. Reference architecture

This is the shape the sources point to for an in-app business assistant. It is close to what the app already has. The differences are in **how steps 2, 4 and 5 are done**, not in the overall flow.

1. **Gate (deterministic).** Check login, kill switch, blocked user, abuse and scope. Use cheap rules or a small classifier. OpenAI calls these "relevance" and "safety" guardrails [S3]. *This app already does this.*
2. **Understand (one structured call, or a fast router).** Turn the message plus the current conversation state into a small typed object, for example `{intent, doctype, filters, group_by, refers_to_previous}`. Use either an embedding router over example phrases [S14] or a single model call that must return JSON matching a strict schema [S4]. Rules stay only as a fast path for very clear cases. Anthropic calls this the "routing" workflow [S1].
3. **Resolve and validate (server).** Check the DocType, fields and options against the site's metadata and the user's permissions. If more than one thing fits, ask with buttons. Never guess. This is "poka-yoke" tool design: make the wrong call hard to make [S1][S2].
4. **Execute (typed, permission-scoped tools).** Use a small set of tools with clear, non-overlapping jobs, strict argument schemas, readable results, and errors the model can act on [S2][S4]. Where possible, use named business measures ("overdue receivables", "sales this month") instead of raw filters. This "semantic layer" idea is what lifts accuracy on business questions [S10].
5. **Answer (grounded).** Numbers, names and totals in the reply come from tool results through templates. The model writes the explanation around them. If a fact was not checked, the reply says so [S6].
6. **Act (human in the loop).** Propose → show a plain-language card → user approves → re-check → execute once → audit [S3][S9]. *This app already does this.*
7. **Cross-cutting.** A structured conversation state object, not text [S7]; a trace per turn [S15]; an evaluation set run on every change [S5]; and cost and latency controls such as model tiering and prompt caching [S1][S8].

## 4. Prioritized recommendations (top 8)

The order is by user impact per unit of effort. None of these needs a rewrite. Each one changes or adds a module behind the current flow.

### 1. Build a real-model evaluation set and run it on every change (M)
- **Why:** UF-15 and UF-16 were found by hand. Without an eval set, every rule or prompt change can break an earlier fix without anyone noticing [S5].
- **How:** Create `erpnext_ai_assistant/evals/cases.yaml` with about 50 cases from the UF tables and chat history: about half in Arabic, run as `sales@`, `accounts@` and `viewer@`, including multi-turn cases ("how many overdue" → "show them" → "export them"). Add `bench --site … execute erpnext_ai_assistant.evals.run`. It calls `run_chat` for each case and grades with code: the DocType and filters in the trace, the number against a direct `frappe.get_list` count, and whether a card was made and for which record. Run each case 3 times and report pass^3. Save results under `docs/` the same way `TEST_RESULTS.md` is kept.
- **Relates to:** UF-15, UF-16, UF-2 (regression), UF-14 (feedback feeds new cases).

### 2. Stop rules from overriding a valid model choice (S)
- **Why:** `canonical_doctype` replaces the model's DocType with a rule match from the user's text on every tool call. When the rule is wrong, the model cannot recover, and multi-DocType questions get forced onto one DocType.
- **How:** In `targeting.py:canonical_doctype`, accept the model's `name` first if it exists, is readable, is not a child table and is not in `DENIED_DOCTYPES`. Use rule matching only to repair an invalid name. Write a trace entry when the rule and the model disagree, then review those entries weekly to decide which side is usually right. Add eval cases for questions that mention two DocTypes.
- **Relates to:** UF-15 (wrong DocType), UF-7 (clarification instead of guessing).

### 3. Build the numbers from tool results, not from the model's wording (S, then M)
- **Why:** A confident wrong number is the worst failure for finance users (UF-15 says so).
- **How (S):** In `agent.py:_finish_with_evidence`, take the numbers in the model's reply and compare them with `signals` totals (count and query). If a number matches no tool total, replace the answer's first line with the `format_count`-style sentence from the tool result, and keep the model's text only as a follow-on explanation.
- **How (M):** Add a strict-schema "plan" step for count and list questions. The model returns `{doctype, filters[], group_by, metric}`. The server validates and runs it, and the existing `targeting` formatters write the sentence. This combines the reliable shortcut path with the model's better understanding.
- **Relates to:** UF-15, UF-6 (content answers), UF-10 (report questions).

### 4. Tighten tool schemas and merge overlapping tools (S)
- **Why:** Strict schemas and enums remove whole classes of bad calls. Fewer, clearer tools mean fewer rounds and lower latency [S2][S4].
- **How:** In `agent.py:TOOL_SPECS`, add `"strict": true` and `additionalProperties: false`. Change `filters` to an array of `{field, op, value}` with an `op` enum. Use an enum of readable DocTypes when the list is small enough, otherwise validate on the server. Merge `list_modules` and `lookup_field` into one `find_field`. Add optional `group_by` and `sum_field` to `count_records`. Replace `{"error": str(exc)}` in `dispatch` with `{error, hint, candidates}` and log the raw exception on the server only.
- **Relates to:** UF-10, UF-15.

### 5. Keep conversation state as data, not text (M)
- **Why:** Follow-ups now work by re-parsing earlier questions with the same rules that pick DocTypes, so any rule miss is repeated on each follow-up [S7].
- **How:** After every count, list, chart or export, store `last_result = {doctype, filters, group_by, total, names[:50]}` in `session_facts_json` from the tool call that actually ran (shortcut or model). In `run_chat.py`, when `refers_back` is true, reuse `last_result` directly instead of joining `last_query` text. Give `last_result` to the model as data. Stop putting `SESSION_FACTS` into the 1,200-char summary. Drop the regex `topic` and `pending_intent="create_lead"` guesses in `conversation.extract_session_facts`.
- **Relates to:** UF-16, UF-9 (open form as context: the open form becomes one more state field), UF-11 (follow-up buttons can call actions with `last_result`).

### 6. Close the remaining write-safety gaps (S)
- **Why:** The approval design is already strong. These gaps are small but real for a multi-user ERP.
- **How:** In `registry.py:propose_write`, store the target's `modified` value on the Pending Action. In `api/chat.py:approve_action`, refuse if it changed. Re-validate update payloads at approval as create payloads already are. Expire `pending` cards after a configurable time. In `writes.resolve_write_target`, when the user's text is generic ("the draft quotation"), list the matches even if the model passed a real name. Show before → after on update cards.
- **Relates to:** UF-2 (known limit), UF-5 (plain cards), UF-12 (`make_*` actions behind the same card).

### 7. Add one replayable trace per turn (S)
- **Why:** Today you can see the steps, but not why a path was chosen, what arguments were sent, or where the 11 seconds went. Traces are also the raw material for evals [S5][S15].
- **How:** Extend the `step()` records in `run_chat.py` into a `trace_json` on `ERP AI Message`: path (shortcut, model or fallback), router confidence, each tool call (name, arguments, total or row count, ms), and each provider call (model, prompt, completion and cached tokens from the `usage` field, ms). Add a System Manager report for slow turns, rule–model disagreements and turns without evidence. Add 👍/👎 on answers and link them to the trace.
- **Relates to:** UF-14, UF-13.

### 8. Cut latency and cost without losing quality (S–M)
- **Why:** How-to answers take about 11 s. The model setting is one global value.
- **How:** (a) In `run_chat.py` and `agent.py:run_tool_loop`, put the static rules first and the dynamic parts (persona tone, memory, session facts, candidate hint) last, so the provider's prompt cache can reuse the prefix [S8]. (b) Index the ERPNext manual into `ERP AI Knowledge Document` on a schedule and search it locally. Until then, fetch pages in parallel and cache by page. (c) Split the model setting into a router or wording model and a tool-loop model, then compare `gpt-4o-mini` with newer small and mid-size models on the eval set before choosing [S1][S3]. (d) Stream the final text to the panel over the existing realtime channel.
- **Relates to:** UF-13.

**Not recommended right now:** replacing Frappe permission checks with a separate access layer; adding raw SQL or text-to-SQL; moving to a multi-agent framework; or replacing the deterministic shortcut path entirely. The current choices are sound, and these changes would add risk without fixing the observed problems.
